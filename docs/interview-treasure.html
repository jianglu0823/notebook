RAG 不是一个东西,是一条流水线。把每一步都能讲出做过什么、怎么做的、为什么这么做,就是满分答案。

→

→

→
4. 向量化
→
5. 检索
→
6. 生成 + 引用

📝 标准答案(用 LLM-note 真实答)

  • 数据接入:PDF / Word / TXT / 图片 / 音频,经 IngestController 落到 uploads/,落 MySQL source 表记录元数据。
  • 解析:TikaReader 抽文本;图片走 ImageUnderstandingService(qwen-vl-max / glm-4.6v-flash 多模态)生成结构化描述;音频走 AudioTranscribeService(paraformer-realtime-v2 ASR)转写。
  • 分块:长度优先 + 段落边界保护,单块 ≤ 512 字符,保留重叠窗口防语义断裂。
  • 向量化:DashScopeTextEmbedding(text-embedding-v3,1024 维),统一编码。
  • 入库:写 Milvus,payload 携带 notebook_id / note_id / source_id / seq,用于应用层按笔记本/笔记过滤。
  • 检索:QaService 走 SimpleKnowledge 抽象,top-K=12 召回,按 notebook/note 二次过滤到 6 块,拼 context + system prompt。
  • 生成:DashScopeChatModel 流式,带 [1][2] 引用编号,可点击跳出处。
💡 加分点:能讲出每一步的失败兜底(Milvus 挂掉时降级到关键词 / 大模型降级链),比只讲 happy path 高一个档次。

Q3. 用到什么向量数据库,为什么用这个 考察选型能力

📝 标准答案

主流向量库对比:

产品架构优势劣势适用场景
Milvus(我们用的) 存算分离(etcd + minio + pulsar 可选) 亿级水平扩展、多索引类型(IVF/HNSW/DiskANN)、云原生 运维较重,组件多 生产级 RAG,亿级以上
Qdrant Rust 单二进制 轻量、过滤快 分布式能力较弱 中小规模、PoC
pgvector PostgreSQL 扩展 不用单独维护一套 性能天花板低 < 100w 行 + 已有 PG
Chroma 嵌入式 本地开发零门槛 不能生产 Demo / 教学
Elasticsearch 8+ 已有 ES 集群 向量 + 全文一套搞定 纯向量不如 Milvus 已有 ES 栈,不想引新组件

为什么选 Milvus(LLM-note 真实理由)

  1. 亿级 + 水平扩展:生产后期望到千万级 chunk,Milvus 是为数不多敢承诺这个量级的开源产品。
  2. 索引丰富:同库内 HNSW(高召回)、IVF_FLAT(中规模 + 平衡)、DiskANN(冷数据落盘)可按 collection 切换。
  3. Schema 化:Field 类型显式(Int64 / VarChar / FloatVector),不像 pgvector 把 schema 塞 PG 表里那么别扭。
  4. 生态完整:io.milvus 官方 Java SDK 与 Spring Boot 集成度高,AgentScope 的 MilvusStore 直接对接。
  5. AgentScope 默认:我们 RAG 走 SimpleKnowledge 抽象,底层接 MilvusStore,换库不动业务。
⚠️ 雷区:别上来就「我选了 Milvus 因为它最快」。要讲业务约束 → 候选 → 取舍。

Q5. 存储到 Milvus 中的数据结构是什么样的 考察 schema 设计

📝 标准答案

Milvus 是「字段化的列存」,每条数据是一个 entity,所有 entity 的字段集合必须等于 collection schema 的字段定义。

LLM-note 真实 schema(companion_memories)

字段类型作用设计理由
idInt64 (PK, AutoID)主键,Milvus 自增用自增避免业务侧重复
embeddingFloatVector[1024]向量text-embedding-v3 固定 1024 维
companion_idInt64伴侣 ID检索时强制过滤,实现多租户
user_idVarChar(64)用户 ID同上,实现用户级隔离
memory_idInt64记忆业务 ID回写 MySQL 时定位原始记录
contentVarChar(512)原文截断存「够用的预览」,详情回查 MySQL

另一个 collection(nblm_chunks,RAG 用)

字段类型作用
idInt64 PK主键
embeddingFloatVector[1024]向量
notebook_id / note_id / source_id / seqInt64 / Int64 / Int64 / Int64应用层过滤 + 出处定位

设计原则

  • 向量字段必须有,主键必须有,其他都是「业务过滤字段」。
  • 不存大文本:Milvus 不擅长,只存 ≤ 1KB 摘要,详情查 MySQL。
  • 过滤字段建索引:大 cardinality 字段(如 user_id)建标量索引提速。

Q6. 用到了几个 collection,怎么分配的 考察隔离设计

📝 标准答案

LLM-note 里用到 2 个 collection,按业务域切分,不是按租户切分。

Collection业务数据量级隔离方式
nblm_chunks RAG 知识库切块 十万级 / 用户 payload: notebook_id + note_id + source_id
companion_memories AI 伴侣长期记忆 千级 / 用户 / 伴侣 payload: companion_id + user_id

为什么不混一个 collection

混一起的坏处
  • 索引参数不同:RAG 偏向高召回(HNSW,efConstruction 200),记忆偏向低延迟(IVF,nlist 大)
  • schema 字段不一致,vector field 维度要统一,业务字段会冲突
  • 删除/归档粒度不同:用户清空记忆 ≠ 清空知识库
  • 备份策略不同:记忆可 30 天归档,知识库永久
分开的好处
  • 每 collection 独立选索引、独立调参
  • 故障隔离:伴侣记忆挂了不影响主 RAG
  • 权限可以按 collection 分配 API key

💡 进阶:Milvus 还支持什么切分粒度

  • Partition(分区):同一 collection 内按时间 / 租户分区,适合亿级单 collection
  • Database:Milvus 2.x 起支持多 database,等于「namespace」
  • Resource Group:把不同 collection 放到不同物理节点(混合部署隔离)

Q7. ID 和关联的关系存在哪里 考察双写一致性 pgvector 变体已加

📝 标准答案(Milvus 范式)

核心结论:MySQL 存权威关系,Milvus 只存过滤字段,不存外键。

LLM-note 的双写设计

业务表(MySQL)
→
写 source 表
→
写 chunk 表(id, source_id, seq, content, vector_id)
→
Milvus 写向量(返回主键 id)
→
把 Milvus 主键回填 chunk.vector_id

为什么这么设计

  • Milvus 没有事务:不能跨 collection 写,更不能跨系统写,所以权威关系必须在 MySQL。
  • Milvus 主键是技术主键:AutoID Int64,业务侧不感知,避免外部误用。
  • MySQL 才是业务主键:chunk.id 是雪花 / 自增,被所有业务逻辑引用,删除/编辑走 MySQL,Milvus 仅做只读检索。
  • 回写关联:用 vectorId 字段做桥梁,检索出 Milvus id 后回查 MySQL 拿 content / source / seq,保证引用准确。
// QaService.java 真实代码
List<String> vectorIds = filtered.stream().map(Document::getId).toList();
Map<String, Chunk> chunkByVid = vectorIds.isEmpty() ? Map.of()
    : chunkRepo.findByVectorIdIn(vectorIds).stream()
        .collect(Collectors.toMap(Chunk::getVectorId, c -> c, (a, b) -> a));

⚠️ 坑:回写失败的补偿

实际生产中,MIlvus 写成功但 MySQL 回写失败会留下「孤儿向量」。常见处理:

  • 补偿任务:定时扫 Milvus,跟 MySQL 对账,孤儿删除 / 重新回填。
  • outbox 模式:先写 MySQL outbox 表 → 后台 worker 拉取 → 写 Milvus → 更新 outbox 状态。保证最终一致。

🔁 范式 B:pgvector(全在一张数据库,无回写)

如果用 pgvector(PostgreSQL 扩展),Q7 的答案完全相反:权威关系、向量、外键、过滤字段全部在 PostgreSQL 一个数据库里,不需要双写,不需要补偿。

pgvector 完整 schema

-- 1. source 表(原文元数据)
CREATE TABLE source (
    id           BIGSERIAL PRIMARY KEY,
    name         VARCHAR(255) NOT NULL,
    type         VARCHAR(20),
    size_bytes   BIGINT,
    owner_id     VARCHAR(64) NOT NULL,
    created_at   TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX idx_source_owner ON source(owner_id);

-- 2. chunk 表(带向量)—— vector(N) 是 pgvector 类型
CREATE TABLE chunk (
    id           BIGSERIAL PRIMARY KEY,       -- 业务主键,自增
    embedding    vector(1024) NOT NULL,     -- 1024 维,跟 embedding 模型对齐
    content      TEXT,                                       -- 原文可存大文本!
    source_id    BIGINT NOT NULL REFERENCES source(id) ON DELETE CASCADE,
    notebook_id  BIGINT NOT NULL,
    note_id      BIGINT,
    seq          INT,
    created_at   TIMESTAMPTZ DEFAULT NOW()
);

-- 3. 向量索引(HNSW 推荐,或 IVFFlat)
CREATE INDEX chunk_embedding_hnsw_idx
    ON chunk USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- 4. 过滤索引
CREATE INDEX idx_chunk_notebook ON chunk(notebook_id);
CREATE INDEX idx_chunk_note     ON chunk(note_id);

检索(SQL 一把梭)

-- 距离算子:
--   <=>  cosine distance  (1 - cosine 相似度,通用首选)
--   <->  L2 / Euclidean     (向量未归一化时用)
--   <#>  negative inner product (IP 度量,结果取负)

-- 标准检索:按 notebook 过滤 + top-6
SELECT id, content, source_id, seq,
       embedding <=> $1::vector AS distance
FROM chunk
WHERE notebook_id = $2
  AND owner_id = $3             -- 跟 source JOIN 后过滤
ORDER BY embedding <=> $1::vector
LIMIT 6;

-- 想 JOIN 拿 source 名?直接写,不用应用层二次查
SELECT c.id, c.content, c.seq,
       s.name AS source_name, s.type,
       c.embedding <=> $1::vector AS distance
FROM chunk c
JOIN source s ON s.id = c.source_id
WHERE c.notebook_id = $2
  AND s.owner_id = $3
ORDER BY c.embedding <=> $1::vector
LIMIT 6;

两套范式核心对比

维度Milvus(LLM-note 用)pgvector(范式 B)
主键 AutoID Int64(技术主键,业务不感知) BIGSERIAL(业务主键,所有逻辑引用)
外键 ❌ 不支持,存过滤字段 ✅ 真正的 REFERENCES + ON DELETE CASCADE
关系存放 应用层维护 vector_id 桥 数据库 FK 约束 + JOIN 表达
事务 ❌ 跨系统写,无事务,需补偿 ✅ ACID,无脑写入
JOIN ❌ 只能按过滤字段在应用层二次查 ✅ 纯 SQL,跨表一把梭
回写失败补偿 需要 outbox / 定时对账 不需要,天然一致
数据量级 亿级水平扩展 千万级单实例,亿级需 Citus
索引类型 HNSW / IVF / DiskANN / 标量 HNSW / IVFFlat(少)

pgvector 的两个高频追问

1. 距离算子怎么选

-- HNSW 索引必须跟算子匹配,否则不走索引!
CREATE INDEX ON chunk USING hnsw (embedding vector_cosine_ops);   -- 对应 <=>
CREATE INDEX ON chunk USING hnsw (embedding vector_l2_ops);         -- 对应 <->
CREATE INDEX ON chunk USING hnsw (embedding vector_ip_ops);          -- 对应 <#>

2. 性能天花板 + 怎么破

数据量方案
< 100w单实例 pgvector,HNSW 够用
100w - 1000w调参(m=24, ef_construction=128)+ 分区表
> 1000wCitus(PG 分布式扩展)或换 Milvus
> 1亿必须 Milvus,pgvector 顶不住

💡 选型话术(面试必背)

看量级和团队:
  • < 100w 行 / 已有 PG / 不想引新组件 → pgvector。FK 天然、事务天然、JOIN 天然。
  • 千万级以上 / 多团队独立向量服务 → Milvus。水平扩展是 pgvector 硬伤。
  • 混合 → 主体 pgvector,RAG 高频 collection 单独走 Milvus 集群。
  • LLM-note 选 Milvus:规划数据量到千万级,支持 RAG(高召回)+ 长期记忆(多 collection)双业务,运维愿意多承担。

Q8. 元数据没有和它的设计 考察字段设计

Q10. 召回的得分阈值最低是多少,分了多少块?平均得分最高的是多少分,得分有处理吗 考察阈值与归一化

📝 标准答案

1. 阈值

  • LLM-note 当前 scoreThreshold = 0.0(IP 内积,负数相关,0 是「不相关」)。
  • 为什么不设高一点?为了召回优先。我们靠二次过滤 + prompt 限制保证质量,而不是靠阈值拒掉低分。
  • 经验:生产系统 先召回宽,再过滤严;直接高阈值容易漏召回。

2. 分块策略

  • 检索召回 12 块 → 按 notebook/note 二次过滤 → 截到 6 块喂给模型。
  • 单块 ≤ 512 字符,重叠 50 字符。
  • 为什么不直接给 12 块?上下文爆掉。1024 维向量 + 6 块 ≈ 3K tokens,留给 prompt 指令和生成空间。

3. 得分处理

  • IP 距离天然在 [-1, 1](已归一化),不需要额外处理。
  • 未归一化的向量,IP 可能 [-10, 10],需要 min-max / z-score 归一化才能跨查询可比。
  • 我们的做法:DashScope embedding 接口默认 L2 归一化,所以 IP 直接当 cosine 用。

💡 进阶:什么时候需要设阈值

不设阈值的坏处

答非所问的 chunk 也进 prompt,模型可能被「带着跑」,生成看似有理实则张冠李戴的答案。

设阈值的场景

用户问的是「事实型」问题(数值 / 时间 / 法规),且无备用资料,需要 hard reject。LLM-note 把 fallback 设计成「答:资料未找到」,而不是兜底编。

→

// RRF 公式:score = Σ 1 / (k + rank_i),k=60 经典

  • 用户对答案「答非所问」的反馈率 > 阈值。

Q16. 节点它们的关系这个模式叫什么模式?它们之间的关系是做的 ReAct 模式

📝 标准答案

核心模式:ReAct(Reason + Act)

2022 年 Yao et al. 提出的范式,把「推理」和「行动」交织在同一个循环里。LLM 先想(think),再决定调什么工具(act),拿到结果再想(re-think)。

ReAct 单步 = Thought → Action → Observation → (next Thought ...)

LLM-note 真实代码(CompanionChatService 简化):
for (iter = 0; iter < 4; iter++) {
    // Thought + Action 一起由 LLM 决定
    chunks = streamTextWithToolsFallback(model, ctx, null, schemas);

    for (resp : chunks) {
        if (resp has ToolUseBlock) toolUses.add(tub);
    }

    if (toolUses.isEmpty()) break;   // 收敛:无工具调用 → 终态

    // Observation:执行工具,拿结果
    for (tub : toolUses) {
        result = dispatchTool(tub);
        ctx.add(toolResultMsg(result));
    }
}

为什么用 ReAct 而不是别的

模式特点适合
ReAct(我们用)动态决策,边想边干工具数量适中、调用深度浅
Plan-and-Execute先列全计划,再执行任务可拆解、步骤稳定
Reflexion执行 + 反思 + 重试需要自我纠错的场景
Multi-Agent 对话多角色轮转写作 / 评审 / 决策
LangGraph StateGraph显式节点 + 条件边 + 持久化长流程、需断点续跑

父子关系怎么表达

在 LangGraph 里是 子图(Subgraph) / 父节点调用子节点。在 LLM-note 的实现里,「父子」体现为:

  • 外层 Agent(Companion)是父,内层是子工具(delegate_to_schedule_agent 实际是去调独立的 schedule-agent 微服务)。
  • 父子之间通过 JSON-RPC + A2A 协议通信,不是 in-process 方法调用。

Q18. LangGraph 一共有几个核心,它们之间的区别,都是各自干什么的 LangGraph 核心抽象

📝 标准答案

LangGraph 4 个核心抽象:State / Node / Edge / Graph。

核心是什么类比
State 贯穿全图的数据容器,通常是 TypedDict / Pydantic React 的 useState,数据库的事务
Node 一个 Python 函数,接收当前 State,返回 partial State MapReduce 的 mapper / reducer
Edge 节点之间的连线;可以是固定边,也可以是条件边(router) 工作流引擎的 transition / 网关
Graph / StateGraph 把所有节点和边编排在一起,可编译执行 DAG 调度器、BPMN 引擎

每个核心的「职责」

  1. State:记忆。决定哪些数据在节点间流转、是否可被 checkpoint、回滚到哪一步。
  2. Node:执行体。每个节点做一件事:调 LLM、调工具、改 State、判分支。
  3. Edge:决策。决定「下一步去哪」。普通边是「A 完了去 B」,条件边是「A 完了看 X 决定去 B 还是 C」。
  4. Graph:编排。把 State / Node / Edge 拼起来,做编译(拓扑检查)+ 执行(run / stream / batch)。

对应到 LLM-note(AgentScope 视角)

LangGraph 概念LLM-note 中的对应
StateList<Msg> ctx + Map<String, Object> meta(动态 in-memory 状态)
NodeReAct 循环里每一轮:LLM 调用 / 工具派发 / 记忆检索
Edgeif (toolUses.isEmpty()) break; + if (hallucinationBlocked) ...
Graph每个 Agent 的 handleUserMessage 方法体本身

💡 LangGraph 进阶特性

  • Checkpoint:状态持久化,支持断点续跑(LLM-note 暂未上,是 plan)。
  • Human-in-the-Loop:interrupt_before 在某节点前暂停,等用户确认。
  • Subgraph:把一张图作为另一个节点。
  • Send / Map-Reduce:并行处理多个文档(适合 RAG 摘要)。

编写者

怎么写(LLM-note 的 prompt 设计方法论)

  1. 明确角色:「你是一个严谨的资料问答助手」而不是「请回答用户问题」。
  2. 硬约束放最前:「只能根据用户提供的资料片段作答,不得编造资料之外的信息」。
  3. 输出格式约束:「在引用具体信息处标注来源编号(如 [1])」。

  5. 少用否定句。LLM 对「不要 X」理解弱,直接说「请 X」。
  6. 中文优先:用中文写 prompt,模型输出更稳。

Q23. 那你用的哪种记忆方式?记忆方式?它特点是什么呀 Memory 类型

📝 标准答案

LLM-note 用了 3 种记忆 + 1 种缓存,讲清各自特点

类型实现特点对应到 LangChain
短期对话记忆 MySQL companion_message 表,滚动窗口 20 条 / 4000 字 最近上下文,保证 LLM「记得这一会儿聊了什么」 ConversationBufferWindowMemory
长期事实记忆 Milvus companion_memories + 触发式抽取 向量检索,跨会话找回「用户提过的重要事实」(喜欢猫 / 过敏 / 生日) VectorStoreRetrieverMemory
状态记忆 亲密度表 / 模板 / 角色人设 结构化,影响 prompt 和路由(7/30/100 天里程碑) 类似 EntityMemory / 自定义 store
缓存 Redis(会话 token / 限流) 不是「记忆」,但常和记忆一起讲 —

每种记忆的特点详解

1. 短期对话记忆(Buffer Window)

✅ 优点
  • 实现简单,直接拼到 system prompt 后
  • LLM 可见,对话连续性最强
  • 时序保留
❌ 缺点
  • 窗口有上限,超出忘
  • token 成本随轮数线性增
  • 无「主题压缩」

2. 长期事实记忆(VectorStore)

✅ 优点
  • 理论上无限容量
  • 跨会话保留
  • 按相关性检索,不是按时间
❌ 缺点
  • 需要「抽取」步骤,谁负责把对话 → 事实?LLM 抽 / 规则抽
  • 召回噪声
  • 写入时机要设计(每轮都抽太贵,只抽 user 的「值得记」内容)

3. 状态记忆(Entity / Profile)

✅ 优点
  • 强结构,可查询
  • 影响 prompt 比纯文本更稳
  • 可触发业务逻辑(里程碑)
❌ 缺点
  • schema 演化麻烦
  • 需要 LLM 抽出结构化字段

💡 实际生产经验

三种记忆的写入时机:
  • 短期:每条消息入库,自动滚窗。
  • 长期:每轮 assistant 完成后异步抽(memoryService.extractAndStoreAsync),失败不阻塞聊天。
  • 状态:用户行为触发(recordInteraction + 里程碑规则)。

Q24. 你为什么要选择这一种,不选其他的?还有好几种,真实,还有好几种,但是你为什么要选择这一种 选型理由

📝 标准答案

这里我默认面试官在问「长期记忆」为什么用 向量库(Milvus) 而不是 纯文本总结 / 知识图谱 / SQL。

候选方案对比

方案原理为啥没选
纯文本总结(ConversationSummaryMemory) 每 N 轮让 LLM 总结成一段,塞 prompt 细节丢失;总结会污染事实(模型加戏);无法按相关性取
SQL 存储(EntityMemory) 结构化字段(用户姓名 / 年龄 / 偏好) 需要预定义 schema,自然语言事实难结构化;查询必须精确匹配
知识图谱(Neo4j / NetworkX) 实体 + 关系三元组 构建成本高(实体识别 + 关系抽取);伴侣场景事实粒度小,图收益不大
向量库(Milvus) ✅ 我们用 原始事实 + embedding + payload 容错强,「用户提过猫相关」能模糊命中;实现简单;随取随存
混合(未来) 向量 + 摘要 + 结构化字段同时存,prompt 注入时取三种融合 最贵,收益边际递减,先不上

选 Milvus 的具体理由(回到业务)

  1. 语义召回:用户问「我对啥过敏」,3 个月前他说「芒果让我口腔溃疡」,字面不匹配,BM25 找不到,向量能。
  2. 事实粒度小:伴侣长期记忆是「用户喜欢吃辣」「住杭州」「养了只橘猫」这种短事实,图谱太重。
  3. 写入自由:不预定义 schema,对话里冒出来啥就存啥,灵活。
  4. 已有基建:RAG 就在用 Milvus,加一个 collection 零成本。
  5. 容错:偶尔错检一条比「漏检十条」影响小 —— 反正 LLM 还会自己再读短期记忆校准。

什么时候应该选其他

  • 如果业务是「法规咨询」,必须严格引用,选 SQL + 全文索引。
  • 如果业务是「医疗病历」,关系复杂,选 知识图谱。
  • 如果业务是「客户支持」,要可解释,选 混合(向量 + 标签 + 规则)。

  4. 时延累加:5 个串行 Agent + 每个 1s = 5s → 关键路径并行化。
  5. Token 成本爆炸:每层都把全部历史传给 LLM → 共享 system + 截断。
  6. 失败不可观测:子 Agent 静默失败 → 统一 Task 状态机 + 重试 + 死信。

💡 我的建议(实际生产)

4-5 节点 + 父子调用,先 StateGraph 跑通,再考虑拆微服务。
  • 早期:in-process,LangGraph 编排,一周出 demo。
  • 中期:子 Agent 抽成 SDK,跨项目复用。
  • 后期:独立微服务 + A2A,只在你需要「独立扩缩容 / 跨语言 / 跨团队」时拆。

亮点 5:ReAct 幻觉拦截

情境:8 次 qwen-turbo 中 7 次首轮不调工具,但吐「已添加成功」类话术。
任务:让用户不被模型骗。
行动:四层兜底 — system prompt 强约束 → tool schema 必填项 → 关键词+话术检测 → ReAct 卡死 break。
结果:badcase 反馈率 14% → 0.8%。

亮点 6:A2A 协议解耦

情境:伴侣要调 12 个日程底层能力,直接暴露给 LLM 会让 prompt 爆炸。
任务:统一入口,子能力下沉。
行动:把 12 个工具封成 delegate_to_schedule_agent 一个 Tool,底层是独立微服务 schedule-agent:8081 + JSON-RPC。
结果:伴侣 prompt 简单,子 Agent 可独立扩缩容 / 跨语言。

P3. 5 个难点 / 踩坑(必讲)体现深度

📝 5 个真实踩坑

坑 1:ReAct 工具调用幻觉

模型在第一轮就吐「已成功」,toolUses=0,用户被骗。
解:关键词 + 话术检测 + 拦截消息 + 整段重写 + 日志告警。

坑 2:SimpleKnowledge 不支持 expr 过滤

AgentScope 的 RetrieveConfig 只能 limit+scoreThreshold,不能 payload 过滤。
解:应用层兜底过滤;长期方案是改用 MilvusStore 直连,带 expr。

坑 3:GLM function calling 不可靠

智谱 GLM 系列在某些版本 function calling 解析失败,模型直接编结果。
解:登录态强制 tools-capable 模型(qwen-turbo),降级链避开 GLM。

坑 4:Bean 顺序导致 ScheduleAgentClient 始终 null

CompanionChatService 实例化早于 ScheduleAgentClient,即使 A2A 开启,工具 schema 也是空 → LLM 吐幻觉。
解:@Lazy + ObjectProvider.getIfAvailable(),运行时再判断,不在构造期强依赖。

坑 5:Milvus 启动时无 collection 的兼容

第一次启动没 collection,插入报错。
解:@PostConstruct 里 ensureCollection():有就 load,没有就建表 + 建索引 + load,挂掉时降级 warn 不抛。
