## 2. Code Quality

### Strengths
- **两段式设计清晰**:阶段 ① 重写 avatar + 顺手按 `parent_ids` 聚合孩子数,阶段 ② 只对超 cap 夫妇清 pregnant。两条独立循环,易读易测。
- **确定性 hash 选 emoji**:不引入"运行时版本号"或"已迁移标记位",`pickAvatar(name)` 本身就是幂等的,重启零代价。
- **防御性 null 检查**:`if (parent.getPregnantSince() != null || parent.getDueDate() != null)` 防止覆盖已经是 null 的字段 → 减少无谓的写库。
- **Javadoc 解释设计意图**:类级注释明确说明"在 EMF 准备好之后、HTTP 监听器启动之前执行(标准 Spring Boot CommandLineRunner 时机)"和"每行 try/catch 不阻塞启动"。
- **测试断言具体且可读**:6 个测试都断言具体行为(reavatar 数、INFO 日志包含的 key=value、字段值),不依赖"没崩就行"的弱断言。

### Minor observations (not blocking)
- **Javadoc 注释中的"在 EMF 准备好之后"** 对没读过 Spring 生命周期的人不够友好。但 CommandLineRunner 的语义就是如此,加更多 Spring 内部细节会偏离"为什么这个 runner 存在"这个注释意图。
- **`mixedDb_reavatarsChildrenAndClearsOverCap` 的 saves=12 而非 14** 略反直觉,因 parent 12/13 原本 pregnant 字段 null → 不被 save。已在测试注释中说明,后续读者能看明白。
- **`lenient().when(repo.findById(anyLong()))` 在 `coupleAtCapOrBelow_doesNotClearPregnantFields` 中** 是因为 couple 恰好 3 == cap 3,清除块 continue,parent 不被加载,strict 模式会报错。改用 lenient 是 trade-off(更宽松 vs. 更显式),后续若 Mockito 提供更精细的"only when called"语义可优化。
